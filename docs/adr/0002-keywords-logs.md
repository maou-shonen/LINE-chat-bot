# ADR-0002：keywords_logs 保留，不加保留期限

狀態：已接受。
日期：2026-11-19（台北時間）

Python 每次成功新增或覆蓋關鍵字，會在 `keywords_logs` 多寫一列。刪除不寫。請求路徑沒有人讀這張表。匯入仍把它列在保留表。這支 PR 要決定 Workers 版要不要繼續寫，或加上保留期限。取捨的理由是寫入列額度，不是功能好不好看。

## 決定

繼續寫 `keywords_logs`。不加保留期限，也不做定期刪除。

成功的新增、覆蓋、疊加各寫一列。記的是這次送進來的內容，不是疊加後的整段。`id` 為 NULL 時不寫，跟 Python 一樣。刪除、查詢、拒絕的指令不寫。

## 為什麼不是額度問題

數字來自 ADR-0001，這支沒有重測正式庫。寫入列上限是每日 100,000。日常寫入約 7,800，約 8%。群組文字每天約 1,450 則。

學習次數沒有單獨量過。就算每一則群組文字都是一次成功學習，每天最多多 1,450 列，是上限的 1.45%。尖峰照 ADR 的 3 倍，也是 4,350 列。離剩下的約 92,000 列還很遠。會改變決定的量級是每天數萬次學習。現在的上限差了兩個數量級。

索引更新也算寫入列。`keywords_logs` 只有主鍵。就算一列實際算成數列，上面的上限仍然遠低於 100,000。這是上限推估，不是量測。

官方定價寫明刪除算寫入列。來源是 [Workers pricing](https://developers.cloudflare.com/workers/platform/pricing/) 的 SQLite storage 註 4，核對日 2026-11-19。保留期限如果靠刪舊列來做，花的是同一種額度，不會幫這條限制省錢。

## 儲存是另一個上限

正式 SQLite 檔是 73.1MB。`keywords_logs` 有 65,415 列。資料表約 15.7MB。主鍵索引約 3.4MB。近一年只新增 191 列。近 30 天新增 7 列。

先前用 LINE 單則 5,000 字、每天 1,450 則全是最長學習來估，一年約 2.6 GB。那是一字一 byte 的放大上限，不是 UTF-8 容量。這次實測已取代那個估算。

[Durable Objects limits](https://developers.cloudflare.com/durable-objects/platform/limits/) 寫明 Free 方案單一 SQLite Durable Object 上限 1GB。超過時寫入回 `SQLITE_FULL`。讀取與刪除仍可用。帳號合計 5GB。

資料表加主鍵索引仍遠低於單一物件 1GB，也遠低於帳號 5GB。結論仍是保留，不設期限。若單一 Durable Object 的儲存（含 `keywords_logs` 與其他表）佔掉 1 GB 的明顯比例，再考慮保留期限。在那之前，刪舊列只是把寫入額度拿去換還用不到的空間。

## 沒有選的做法

停寫。可以少掉這 1,450 列上限裡的寫入，但新學習不再有紀錄，也跟 Python 和匯入保留表不一致。額度沒有逼到這一步。

加保留期限。刪除算寫入列，所以它不解決這支 PR 要看的額度問題。
